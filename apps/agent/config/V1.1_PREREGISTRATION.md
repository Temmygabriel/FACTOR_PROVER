# v1.1 research phase — preregistration

**Written:** 2026-09-26, before any v1.1 hypothesis was tested.
**Policy file:** `apps/agent/config/gate_policy.v1.1.json`
**Policy sha256:** `sha256:5efb3dbbbd1dce3ac5356e66122a88003f3d96cc8bb014156af821a3e55ff854`

This document and the policy file it names were committed **before** the sweep ran.
The git history is the evidence for that ordering: the commit that adds this file
contains no v1.1 result, and the commit that adds `logs/v1.1.jsonl` comes after it.
If the ordering is ever doubted, `git log --diff-filter=A -- apps/agent/logs/v1.1.jsonl`
answers it.

---

## 1. Why a second policy version exists at all

The v1.0 phase ended with one promoted factor (`H-0006`, ETH spot momentum →
**RGOOGLUSDT**) and that factor did not survive out of sample. It also could never
have been executed, and that second fact is independent of the statistics:

> Every rToken is refused by the Bitget demo venue before any sizing or balance
> check — `HTTP 400 from Bitget: papTradingService not support RWA order validation
> error` — and `RTOKEN_SYMBOLS` is the only target list the protocol can express.

So the promoted factor was guaranteed unexecutable **before it was proposed**. No
execution-side fix exists for that; the mismatch is between the protocol's target
universe and the venue's instrument support.

`BTCUSDT` is the one instrument this project has verified its Agent Hub path can
actually place an order on (accepted demo orders `1485970832289546240` and the one
before it). v1.1 therefore targets it.

**The motive is disclosed, not implied.** Choosing a target because it is the one
that can execute is a specification choice made with knowledge of the venue. It is
recorded in the policy file's `target_universe_rationale` field as such. It does not
bias the statistics — the same engine measures the same thing on the same frozen
bytes — but a reader is entitled to know why this target and not another, and a
version of this document that presented BTCUSDT as a data-driven discovery would be
the exact dishonesty this project is built to avoid.

**ETHUSDT is deliberately excluded.** It is a reference coin whose candles this
system already reads, so adding it would have been cheap. Its venue reachability has
never been verified. Assuming it would repeat the mistake this list exists to
prevent.

## 2. What changed from v1.0, and what did not

A reader can check this claim by diffing the two policy files rather than trusting
it. Only four things differ:

| | v1.0 | v1.1 |
|---|---|---|
| `policy_version` | `v1.0` | `v1.1` |
| `locked_at` | `2026-09-11T00:00:00Z` | `2026-09-26T00:00:00Z` |
| `target_universe` | *(absent — defaults to the 7 rTokens)* | `["BTCUSDT"]` |
| `families_enabled` | the three `*_rtoken` families | the three `*_pair` families |

Plus prose: the lock rationale, the `v1_1_changes` disclosure block, the
`research_protocol` block, and an added note in `power_analysis`.

**Every threshold is byte-identical.** `fdr_level` 0.10, `min_ic` 0.04,
`min_t_stat` 2.0, `min_obs` 100, `require_baseline_beat` true, `sampling`
`non_overlapping`, the five-element `kill_reason_precedence`, the whole
`circuit_breaker` block and the whole `execution_guard` block are copied unchanged.

**No threshold was loosened.** The instruction that produced this phase was explicit
that the goal is to find a real surviving factor, not to force one, and the strongest
available evidence for that is that the file which would have to contain a loosened
threshold contains none.

**v1.0's file is untouched.** `gate_policy.json` still hashes to
`sha256:2b49be0d6688f8588aa56b095ad399472cb7e1e533a9fd0301f71aca351d8e15`, which is
the value recorded in every one of the 201 entries in `logs/decisions.jsonl`. It
could not have been edited: adding a `target_universe` key to it would change its
bytes and leave the published record unable to name the policy it ran under. That is
why the new version is a new file, and why the *absence* of the key is what makes
v1.0's behaviour the default.

**Family names are new, not widened.** A durable record entry reading
`funding_to_rtoken` must keep meaning *a funding signal tested against a tokenised
equity*. v1.1 tests against a venue pair, so it gets `funding_to_pair`,
`momentum_to_pair`, `combined_to_pair`. The v1.0 names and their signal licences
remain in the code and remain valid; nothing was reinterpreted.

## 3. The preregistered family

The enumeration is mechanical, and the condition templates and lookbacks are
**imported from `src/llm/deterministic.ts` rather than retyped** — a re-declared
threshold table could silently test a different space while reporting that nothing
else changed.

```
for family in {funding_to_pair, momentum_to_pair, combined_to_pair}:
    for signal in FAMILY_SIGNALS[family]:
        for target in ["BTCUSDT"]:
            for (operator, threshold) in the v1.0 condition templates:
                for forward_window in FAMILY_WINDOW_BOUNDS[family]:
                    for lookback in [30, 60, 120, 240]:
```

`direction` is `positive` for a `gt` condition and `negative` for an `lt` one,
exactly as v1.0's enumerator assigns it.

**Size: 320 hypotheses.**

| family | count |
|---|---|
| `funding_to_pair` | 160 |
| `momentum_to_pair` | 120 |
| `combined_to_pair` | 40 |

| signal | count |
|---|---|
| `btc_funding_rate` | 80 |
| `eth_funding_rate` | 80 |
| `btc_spot_return` | 60 |
| `eth_spot_return` | 60 |
| `btc_funding_x_spot` | 40 |

Order is the natural nested-loop order rather than v1.0's strided walk. The stride
existed to spread a model-outage fallback's *consecutive* proposals across the space;
here the whole space is swept, so there is no sequence of consecutive proposals to
spread.

**The 60 `btc_spot_return → BTCUSDT` candidates are included, and predicted to die
structurally.** For that combination the signal is computed from BTCUSDT's own
candles over the condition's lookback, and the engine's naive baseline is *the target's
own trailing return over the same lookback*. Those are the same number. So
`|IC| == |baseline_IC|` by algebra, and `require_baseline_beat` kills it before any
evidence is considered.

They are kept in the family rather than hand-excluded for two reasons: excluding them
requires a special case, and special cases in a preregistered enumeration are how
specification search hides; and as 60 guaranteed kills they are a positive control
that the baseline check is not dead code. The prediction is recorded here, before the
run, so that reporting it afterwards is a confirmation rather than a story.

## 4. Multiplicity, stated before the result

The Benjamini–Hochberg correction is family-wide. With m = 320 and FDR 0.10, the
threshold at rank 1 is

```
0.10 / 320 = 3.125e-4
```

That is a strict bar, and it is the honest consequence of testing 320 hypotheses —
not a reason to test fewer. If nothing clears it, the correct report is that nothing
cleared it.

The 60 structural kills inflate m. Without them the rank-1 bar would be
`0.10 / 260 = 3.846e-4`. Both figures are reported so a reader can see that the
choice to include the controls neither manufactured nor hid a promotion.

**The family is fixed before the first backtest**, which changes the shape of the
result relative to v1.0. v1.0's loop grew its family one attempt at a time, so BH was
re-applied after every attempt and a hypothesis could be promoted and later demoted as
the bar tightened — which is exactly what happened to `H-0006` between `E-0006` and
`E-0008`. Here m is 320 for every adjudication, so no demotion dynamic can arise. That
is a consequence of sweeping exhaustively, not a convenience.

BH's validity assumes positive dependence among the tests, which holds here in the
approximate sense that matters: the candidates are nested variants of a small number
of underlying signals, so their p-values are strongly positively correlated. This is
disclosed rather than asserted.

## 5. The two stages

**Stage 1 — DISCOVERY.** All 320 hypotheses, on the frozen store, adjudicated
family-wide at m = 320. A hypothesis survives only by clearing every preregistered
check.

**Stage 2 — VALIDATION.** Read **only** for stage-1 survivors, adjudicated at
m = the number of survivors. If stage 1 promotes nothing, **VALIDATION is not read at
all.**

That second sentence is the load-bearing one. Every one of the 201 entries in the
v1.0 record used DISCOVERY; VALIDATION has never been read by any recorded result in
this project. It is the only unspent partition left. Reading it to search for
something after a null stage 1 would be exactly the specification search this
preregistration exists to prevent, so the script refuses to.

**LOCKED_TEST is not read.** It was spent by the v1.0 out-of-sample pass on
2026-09-25 (`logs/locked-test.jsonl`) and is not reusable. v1.1 makes no
out-of-sample claim from it.

---

## 6. The running system is not switched

v1.1 is a **research phase**. The LLM prompt, the schema validator and the session
loop continue to offer and accept the rToken universe, because switching production to
a new policy version is a separate change with its own blast radius and its own
disclosure. A reader of `/api/status` or the deployed dashboard is looking at v1.0 and
should be told so.

## 7. Predictions, recorded before the run

Recorded so that they can be checked against the result rather than fitted to it:

1. The 60 `btc_spot_return → BTCUSDT` candidates will all be killed with
   `baseline_not_beaten` (or `insufficient_obs` where the condition selects too few
   events, which takes precedence).
2. Observation counts will be **higher** than v1.0's rToken figures at the same
   forward window, because BTCUSDT trades continuously while rTokens collapse to
   2–8% coverage on weekends. If they are high enough at the 15-minute window, the
   `min_ic` floor of 0.04 — which v1.0's own note says "only binds once n >= ~2500" —
   may bind for the first time.
3. Funding-rate candidates will mostly die on `t_stat_below_floor` or
   `ic_below_floor`, as they did in v1.0 (73 IC-floor kills and 58 t-floor kills of
   201).
4. Most likely outcome: **zero survivors at m = 320.** A rank-1 bar of 3.125e-4 is
   not cleared by noise, and that is the point. A non-empty stage 1 would be a
   genuinely surprising result and would be reported as such.
